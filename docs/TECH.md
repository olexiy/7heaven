# 7Heaven — Технические решения и план реализации

> Версия: 0.2 (приведено в соответствие с кодом v0.2)
> Дата: 04.09.2026
> Этот документ отвечает на вопрос «как». На вопрос «что» отвечает `GDD.md`, на вопрос «что сейчас» — `MVP.md`.

---

## 1. Главная идея реализации

**Игра — это детерминированная симуляция, к которой прикручен рендер.** Ядро игры не знает о браузере, холсте и мыши. Оно принимает команды, тикает фиксированным шагом и порождает события. Браузер лишь рисует состояние и переводит клики в команды.

Из этого следует три вещи, которые отличают этот прототип от «чуши»:

1. **Бой можно прогнать без экрана.** Тысячу боёв за секунду, в Node, с отчётом: кто победил, за сколько секунд, сколько срывов. Баланс проверяется цифрами, а не ощущениями.
2. **Всё воспроизводимо.** Семя генератора + журнал команд = точное повторение забега. Любой баг превращается в тест.
3. **Правила — это данные.** Умение, действие, враг, модификатор — записи в файлах данных с типами. Движок их исполняет, а не содержит. Добавить новое заклинание — значит добавить запись, а не переписать бой.

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Язык | **TypeScript** (strict) | типы на данных правил ловят ошибки до запуска; конвейер модификаторов без типов превратится в кашу |
| Сборка | **Vite** | секунда на запуск, горячая перезагрузка, статический билд одной папкой |
| Рендер | **Canvas 2D** через тонкий интерфейс `Renderer` | ноль зависимостей, изометрия и частицы рисуются напрямую; когда появятся спрайты, за интерфейсом встанет PixiJS без правки ядра |
| Интерфейс | **HTML/CSS поверх холста** | панели, кнопки скорости, полоски HP — это DOM, а не пиксели; дешевле и доступнее |
| Тесты | **Vitest** | запускает ядро без браузера |
| Зависимости в рантайме | **ноль** | прототип должен открываться одним файлом и не ломаться от обновления библиотек |
| Хостинг | статическая папка | открывается локально, кладётся на любой хостинг без бэкенда |

Отвергнуто: Phaser (тащит свою модель игрового цикла, конфликтует с детерминированной симуляцией), Unity/Godot (цикл «написал → увидел» в разы медленнее для проверки концепта), React для игрового поля (не для этого сделан).

## 3. Архитектура

```
src/
  core/            чистый TypeScript, ни одного импорта из DOM
    time.ts        тик 50 мс, перевод секунд в тики
    sim/           Sim: цикл тика, семя (rng.ts), команды, журнал, replay, восприятие, слух
    world/         карта (map.ts), генерация (mapgen.ts), поле зрения (fov.ts), A* (path.ts)
    entity/        Entity: каналы, атрибуты, навыки, направление взгляда, откаты
    action/        action.ts (типы), engine.ts (старт, фазы, отмена, прерывание), resolve.ts (удар, заклинание, урон, блок, опыт)
    rules/         modifiers.ts (конвейер), collect.ts (сбор модификаторов), risk.ts (словесная оценка)
    ai/            автоатака и автопилот, общие для игрока и врагов
    events.ts      события, которые ядро отдаёт наружу
  data/            actions.ts (действия и приёмы), entities.ts (игрок, гули, шаман), rules.ts (модификаторы и базовые числа)
  render/          iso.ts (проекция), canvas.ts (тайлы, туман, сущности, кольца, частицы)
  ui/              hud.ts: DOM-панели, кнопки, откаты, строка риска
  app/             main.ts (склейка, события → эффекты, отладочный хук), loop.ts (пауза, скорости, автоперемотка)
tools/
  sim-cli.ts       прогон боёв без экрана, отчёт по балансу
  diag-timeout.ts  поиск рифтов, где автопилот застрял
  screenshot-plugin.ts  dev-плагин Vite: POST /__screenshot сохраняет PNG в docs/screenshots
tests/
  world/           генерация, поле зрения, путь (+ fixtures.ts: карта из ASCII)
  core/            движение, детерминизм, replay, слух
  rules/           статистические тесты правил конвейера (+ helpers.ts: манекены без ИИ)
```

Правило зависимостей: `core` ни от чего не зависит; `data` зависит только от типов `core`; `render` и `ui` зависят от `core`; `app` собирает всё.

### 3.1 Время

- Фиксированный тик **50 мс** игрового времени (20 тиков в секунду). Достаточно для действий длиной от 0.5 с и даёт стабильную математику.
- Кадр реального времени накапливает дельту, умножает на масштаб (0 = пауза, 1, 2, 5, 10) и выполняет столько тиков, сколько накопилось. Рендер интерполирует между тиками для плавности.
- Все длительности и таймеры внутри ядра — в тиках, наружу переводятся в секунды.

### 3.2 Детерминизм

- Один генератор случайных чисел с семенем на всю симуляцию (mulberry32 или xoshiro).
- Ядро принимает команды только через `sim.command(tick, cmd)`. Журнал команд сохраняется.
- `replay(seed, commands)` воспроизводит забег тик в тик. Это основа тестов и отладки: «на 412-м тике фаербол сорвался, хотя не должен» превращается в падающий тест.

### 3.3 Сущности и каналы

```
Entity {
  id, pos, hp, mana, alive
  attributes: { str, agi, end, int, wis, per }
  skills: Map<skillId, { level, xp }>
  channels: Map<'legs' | 'rightHand' | 'leftHand', ActionInstance | null>
  statuses: Set<'moving' | 'shielded' | 'wounded'>
  facing: { dx, dy }               // направление взгляда; isBehind(x, y)
  cooldowns: Map<actionId, tick>   // восстановление: когда действие снова доступно
  visible: Set<tileIndex>          // поле зрения, пересчитывается каждый тик
  awareness: 'unaware' | 'alert' | 'combat', lastSeenTarget, reactUntil
  path: Vec[]                      // очередь шагов
}
```

Действие занимает каналы на время выполнения. Жёстких правил три: каналы свободны, действие не в восстановлении, хватает маны. Всё остальное — модификаторы.

Разум пока не отдельный канал: заклинания занимают обе руки, этого достаточно, чтобы щит и каст были несовместимы.

### 3.4 Действия как автоматы

```
ActionDef {
  id, name, kind: 'step' | 'melee' | 'shield' | 'spell'
  category: 'action' | 'ability'      // действие (доступно автоатаке) или приём (только вручную)
  channels: channelId[], cooldown?, cost: { mana? }, skill?
  range?, needsLos?, damage?, interruptChance?, damageReduction?, noise?
  phases: PhaseDef[]                  // одна фаза для удара, три для заклинания
}
PhaseDef {
  id, baseDuration, interruptible, failBase, onCancel: 'keep' | 'loseAccumulated' | 'loseAll'
}
```

Экземпляр действия хранит текущую фазу, оставшиеся тики, цель и накопленное (мана). Каждый тик: уменьшить остаток, проверить срыв в конце фазы, перейти дальше или разрешить.

Старт действия разворачивает тело к цели; если цель за спиной, к первой фазе добавляется время разворота. Восстановление (`cooldown`) стартует, когда действие завершилось, сорвалось или было прервано, но не при ранней отмене.

Разрешение удара: попадание → уклонение (невозможно, если цель не видит атакующего или её ноги заняты) → крит → урон → полный блок щитом (шанс от навыка, невозможен со спины) → снижение урона щитом → прерывание, если действие умеет.

### 3.5 Конвейер модификаторов

```
Modifier {
  stage: 'ready' | 'prepare' | 'phase' | 'resolve' | 'after'
  param: string                       // 'duration', 'failChance', 'hitChance', 'damage' …
  op: 'add' | 'mul'
  value: number
  when?: (ctx) => boolean             // условие: 'actorMoving', 'targetCantSee' …
  source: string                      // откуда: умение, статус, предмет
}
```

`resolveParam(param, base, ctx)` собирает модификаторы от всех источников контекста (атрибуты, умения, статусы, окружение, цель), фильтрует по условию, применяет сначала `add`, затем `mul`, возвращает значение и **след** — список применённых модификаторов. След нужен для отладки и для словесной оценки на кольце: «рискованно, потому что вы движетесь».

Параметры конвейера: `duration`, `failChance`, `hitChance`, `dodgeChance`, `damage`, `damageTaken`, `interruptChance`, `blockChance`, `critChance`. Источники: `skillModifiers`, `statusModifiers`, `targetModifiers`, `blockModifiers` в `data/rules.ts`. Оценка риска (`rules/risk.ts`) прогоняет тот же конвейер без бросков кубика и переводит вероятность в три слова.

Умение — это список модификаторов, зависящих от уровня. Статус «движется» — это модификатор `phase.failChance ×20`. Всё одним языком.

### 3.6 Мир

- Карта: сетка клеток `floor | wall`, генерация комнат случайным размещением с соединением коридорами, гарантия связности проверяется заливкой.
- Поле зрения: рекурсивное теневое отбрасывание (shadowcasting) с радиусом от Восприятия. Считается для игрока и для каждого врага.
- Поиск пути: A* по клеткам, восемь направлений, диагональ дороже.
- Изометрия — только в рендере. Ядро живёт в квадратной сетке; проекция `(x, y) → (x − y, (x + y) / 2)` применяется при отрисовке и обратная при клике.

### 3.7 ИИ

Состояния `unaware → alert → combat`. Переходы по событиям восприятия (увидел, услышал шум). В бою — приоритеты из GDD, задержка реакции `база ÷ Восприятие` в тиках. ИИ использует те же действия и тот же конвейер, что и игрок: никакого «читерства» врагов.

Две функции в `ai/ai.ts`:
- `autoAttack` — заполняет свободные каналы сильнейшим готовым **действием** против врага рядом; удар ногой бережёт для кастующей цели. Используется автоатакой игрока и ИИ врагов.
- `aiStep` — полный автопилот: щит при половине HP и замахе врага, прерывающий приём против кастера, заклинание с дистанции (кастер стоит на месте и отходит от врага), подход.

Слух: событие `noise` из ядра сразу вызывает `sim.hear`: враги в радиусе становятся `alert` и идут к источнику.

### 3.8 События

Ядро не рисует и не пищит. Оно публикует события: `ActionStarted`, `PhaseChanged`, `ActionFailed`, `Hit`, `Missed`, `EntityDied`, `EnemySpotted`, `NoiseHeard`. Рендер подписывается на них для частиц и вспышек, интерфейс — для подсказок, автоперемотка — для остановки времени.

## 4. Рендер

- Один холст, слои по порядку: тайлы → туман → предметы и выход → сущности с сортировкой по глубине → кольца → частицы → выделение.
- Кольца: три радиуса (правая рука 10, левая 14.5, ноги 19), дуги `arc()` с секторами фаз, цвет по типу действия. Заклинание занимает обе руки и рисуется одним кольцом. Клик по кольцу отменяет действие канала.
- Направление взгляда: клин у ног в проекции направления.
- Холст сам подгоняет размер на каждом кадре: в скрытой панели браузера `clientWidth` равен нулю.
- Частицы: простой пул точек с временем жизни; хватает для трёх фаз заклинания и срыва.
- Интерполяция: позиция сущности рисуется между предыдущим и текущим тиком по доле накопленной дельты.
- Плейсхолдеры: ромбы-тайлы, фигуры-сущности с цветом по типу. Позже сюда встают спрайты без изменения ядра.

## 5. Проверка качества

### 5.1 Три судьи

| Судья | Что проверяет | Как |
|---|---|---|
| **Тесты ядра** | правила работают как написано | Vitest: «каст на бегу срывается в 20 раз чаще», «щит режет 70 %», «удар ногой прерывает только накопление» |
| **Прогон боёв** | баланс и играбельность | `sim-cli`: 1000 боёв «игрок на автопилоте против двух врагов», отчёт по победам, длительности, срывам |
| **Глаза** | ощущение | запуск в браузере, скриншоты ключевых моментов, оценка читаемости колец и тумана |

### 5.2 Что считается «работает»

Не «код скомпилировался», а: тесты зелёные, прогон показывает ожидаемые числа, скриншот подтверждает картинку. Каждый этап заканчивается всеми тремя проверками.

## 6. Процесс разработки

### 6.1 Вертикальные срезы

Не «сначала весь движок, потом весь рендер», а тонкий срез через все слои, который можно запустить и увидеть. Каждый срез оставляет игру в рабочем состоянии.

| Срез | Результат, который можно увидеть | Статус |
|---|---|---|
| 1. Скелет | карта генерируется, персонаж ходит по клику, пауза и скорости работают, туман | ✅ |
| 2. Тело | каналы, удар мечом, кольцо над персонажем, отмена | ✅ |
| 3. Конвейер | модификаторы, попадание против уклонения, щит, первый враг с ИИ | ✅ |
| 4. Магия | огненный шар с тремя фазами, мана, срыв при движении, частицы | ✅ |
| 5. Симуляция | враги с восприятием, шум, автопилот, прогон боёв, выход и смерть | ✅ |
| 6. Опыт | правило вызова для четырёх умений, рост ощущается как ускорение | ✅ |
| 7. Полировка | подсказки, читаемость, скриншоты | ✅ (без звука) |
| v0.2 | откаты, автоатака, три канала, блок, удар щитом, шаман, взгляд, пауза по приёму | ✅ |

### 6.2 Цикл на срез

```
спецификация среза (из MVP.md)
  → тесты на правила среза (сначала падают)
  → реализация
  → тесты зелёные
  → прогон боёв, если срез трогает бой
  → запуск в браузере, скриншоты
  → оценка: что не так, что подкрутить
  → фиксация (commit)
  → следующий срез
```

### 6.3 Автоматизация

- **Git с первого среза.** Каждый срез — коммит с описанием. Откат всегда возможен.
- **Проверки одной командой:** `npm test`, `npm run sim`, `npm run dev`.
- **Отладочный хук** `window.game`: `advance(сек)` гонит симуляцию синхронно, `shot(имя)` сохраняет скриншот с HUD через dev-плагин. Нужен, потому что в скрытой панели встроенного браузера не работают `requestAnimationFrame` и клики по холсту; игровой цикл поэтому имеет запасной таймер.
- **Статистические тесты правил:** вероятности проверяются на сотнях семян с допуском, а не единичным броском.
- **Параллельные агенты** для независимых модулей, когда это ускоряет: генерация карты и поле зрения не зависят от конвейера модификаторов, их можно писать одновременно и собрать в срезе. Интеграция — всегда в одном потоке.
- **Данные правил** пишутся так, чтобы их можно было генерировать: у каждого файла данных есть схема и валидатор. Новый враг, сгенерированный по описанию, либо проходит схему и прогон, либо отклоняется.

### 6.4 Что делается позже и не мешает сейчас

- Спрайты: генерируются по описаниям, кладутся за интерфейс `Renderer`.
- Сохранение: сериализация состояния ядра, оно уже чистые данные.
- Комната: отдельный режим поверх той же симуляции времени с другим масштабом.
- PixiJS: замена реализации `Renderer`, когда спрайтов станет больше, чем тянет Canvas 2D.

## 7. Риски и как они закрыты

| Риск | Закрытие |
|---|---|
| Реальное время нечитаемо, игрок не успевает | кольца показывают будущее; пауза мгновенна; автоперемотка убирает пустое ожидание; проверяется скриншотами и прогоном |
| Конвейер модификаторов разрастётся и станет непонятным | след модификаторов на каждом расчёте; тест на каждое правило; числа только в данных |
| Детерминизм сломается из-за плавающей точки | все длительности в целых тиках, случайность только из одного генератора, тест на воспроизведение забега |
| Изометрия усложнит клики и сортировку | ядро в квадратной сетке; проекция и обратная проекция в двух функциях с тестами |
